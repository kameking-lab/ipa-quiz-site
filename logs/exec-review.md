### 5. 岡本 弁護士（50 / 兼業・労務問題専門）

**スコア**: A=7 / B=4 / C=6 / D=4 / E=3 → **計 24 / 50**

兼業の観点から最重要な所見を述べる。**「教育貢献プロジェクト」のラベリングと、運営者が本業（恐らく雇用形態の労働者）であることの整合性が、運営者の所属企業の就業規則次第で大問題になり得る**。

日本企業の就業規則の多くは「副業を許可制または届出制」とし、「会社の利益と相反する活動」「営利目的の活動」を制限する。本サービスは:

1. **形式上は無償**: 金銭収入なし → 一見、就業規則上の「副業」に該当しない
2. **しかし継続的・反復的**: GitHub の commit 履歴、note 連載、X アカウント（@kakomon_ai_jp）の存在 → 客観的には「事業活動」と評価される余地
3. **「非営利」の自称**: 法的には「非営利」は法人格（NPO法人・一般社団法人）の問題であり、個人が「私は非営利です」と宣言しても法的効果はない

つまり、就業規則違反の判定は「収入の有無」ではなく「活動の実態と継続性」で行われる。本サービスは外形的には事業活動の構成要件を満たしている（継続性・反復性・営利性の構成要素のうち 2/3）。所属企業から見れば「副業申告漏れ」と認定される可能性は十分にある。

第二に、運営者が兼業申告をしている場合でも、「将来 PAID_MODE=true で課金開始する設計」が見えると「将来の競合事業を仕込んでいる」と評価される。特に運営者の本業が IT 教育・SaaS・コンサル系である場合、職務専念義務違反・競業避止義務違反の論点が生じる。

「個人事業主としての独立可能性」を視野に入れているなら、現時点での税務署への開業届と、所属企業への副業申告書類の整備を強く推奨する。

**致命的指摘 TOP3**:
1. 「無償だから副業ではない」は法的には誤認
2. PAID_MODE 復活シナリオが「将来の競合事業」リスクを内包
3. 利用規約の責任制限条項（特に AI 採点の誤りに対する免責）が薄い

**改善 TOP3**:
1. 所属企業への副業申告状況を社内文書化
2. 利用規約に「AI 採点は参考情報であり、合否判定の根拠としない」を明記
3. 運営主体を個人 → 一般社団法人 / 任意団体に移行する選択肢を 6 ヶ月以内に検討

**結論**: 法的リスクは「グレー」だが、所属企業との関係次第で黒に転ぶ。NPS = -20。

田島 CFO の指摘と重複する点は省き、税務実務に特化して補足する。

第二に、「教育貢献プロジェクト」「非営利」のラベリングは、**屋号として登記されていない以上、税務上の意味を持たない**。屋号は自由に名乗れるが、それを根拠に「私は非営利だから収入計上不要」と主張することはできない。仮に将来アフィリエイト収入（CLAUDE.md 13 章で言及されている `safeaisite22-22` Amazon タグ）が発生した場合、**1 円でも収入があれば事業所得**として申告対象。

第三に、姉妹プロジェクト（ANZEN AI / safe-ai-site）と「Vercel 環境・アフィリエイト枠を共有」と CLAUDE.md に明記されている。これは「同一運営者による複数事業の収支通算」を意味するため、損益通算と消費税課税対象判定（年商 1,000 万超のリスク）の準備が必要。

第四に、フィードバックゲートで AI 利用が「無制限化」される設計は、**運営側の API コストが事実上「ユーザー労務（フィードバック執筆）」と交換される構造**になっている。これを「物々交換」と認定された場合、課税論点が発生し得る（実務上は争われないが、利用規約で予防する価値あり）。

**致命的指摘 TOP3**:
1. 開業届未提出（推定）→ 経費化機会の損失
2. 姉妹プロジェクトとの収支通算プロセスが不在
3. アフィリエイトタグの会計処理が未整理

**改善 TOP3**:
1. 開業届提出 + 屋号「過去問AI」を税務署登録
2. 月次収支表（収入 0 / 支出明細）を 12 ヶ月分残す（青色申告 65 万円控除狙い）
3. 利用規約に「フィードバックは無償の意見表明であり対価関係を構成しない」と明記

**結論**: ピボット自体は税務的には中立。ただし会計実務の整備不足が露呈。NPS = -5。

2. /operator に「運営: 個人 1 名」「2026 年から運営継続中」「仮に停止する場合は 30 日前に告知」と明記

**結論**: 受験生としては嬉しい。法人で使えるかは別問題。NPS = +50。

### 9. 鈴木さん（45 / 元 IPA 採点者 / 試験運営側の視点）

**スコア**: A=5 / B=6 / C=7 / D=4 / E=4 → **計 26 / 50**

IPA 試験の採点に従事した経験から、現サービスの最大の問題点は**「AI 採点の妥当性検証プロセスが完全に不在」**であること。記述式・論文式の採点基準は IPA 公表していないが、現場では「キーワード必須要素」「論理展開」「字数バランス」など定量化された基準が存在する。Gemini に IPA 試験の答案を採点させても、それは「Gemini が考える妥当な採点」であって、IPA の採点基準ではない。

「教育貢献」を謳って受験生に AI 採点を提供することは、**間違った合格イメージを植え付ける可能性**がある。例えば AP 午後の問題で AI が「合格圏内」と判定した答案が、本番では不合格点という事態は容易に起こる。逆も然り。これは教育的には有害であり得る。

第二に、IPA 公式問題の利用について。IPA は「使用許諾不要・使用料不要」を明示しているが、「翻訳・改変は認めない」「商用利用には別途相談」など細則がある。本サービスが「教育貢献プロジェクト」「非営利」を謳い続ける限り問題は薄いが、PAID_MODE=true で再有料化した瞬間に IPA との関係見直しが必要。/about に「IPA に確認済み」と書ける状態にあるかは疑問。

第三に、解説文の品質。サンプルとして AP 午前問題の解説を読んだが、Gemini 生成と思われる文章には「IPA の採点観点と異なる説明」が散見される。教育的には致命傷ではないが、競合「過去問道場」の人力解説と比べて学習効果で優位とは言えない。

**致命的指摘 TOP3**:
1. AI 採点の妥当性検証プロセス不在 → 受験生への悪影響リスク
2. IPA 公式問題の利用条件と PAID_MODE 復活時の整合性が未整理
3. AI 生成解説の品質保証プロセス不在

**改善 TOP3**:
1. AI 採点に「これは AI による参考評価であり IPA 公式採点とは異なります」を必須表示
2. IPA に正式に問い合わせ、回答内容を /about に転載
3. 解説文の人力レビュー体制（少なくとも頻出問題 100 問）を構築

**結論**: 教育的に責任ある運営とは言えない。NPS = -20。

### 10. 渡辺さん（34 / SaaS スタートアップ CTO / AP 合格済 / 技術観点）

**スコア**: A=7 / B=5 / C=8 / D=5 / E=5 → **計 30 / 50**

CTO 視点で技術設計を辛口に評価する。

良い点: PAID_MODE フラグの設計は教科書的に正しい。`lib/paid-mode.ts` で集中管理し、`if (!PAID_MODE) notFound()` を各ルートで分岐する設計は、フィーチャーフラグのアンチパターンを踏んでいない。Stripe 連携・SAML 認証・DPA テンプレートを全て温存しつつデプロイから切り離せる構成は、スタートアップの「優先度ピボット」の手本。

しかし致命的に弱いのは:

1. **メタデータがガード外**: `app/admin/team/page.tsx` の `export const metadata` は無条件 export。PAID_MODE=false 時、ルート自体は notFound() になるが、Next.js のメタデータ解決は別レイヤで動く可能性があり、**ビルド成果物に「Team プラン」文字列が SEO 用として残存する**懸念。実害は小さいが、ピボットの「徹底度」を主張する以上、不徹底は信頼を毀損する。

2. **フィードバックゲートのバイパス容易性**: localStorage の `x-feedback-submitted` フラグだけで判定しているため、開発者ツールで `localStorage.setItem('feedbackSubmitted', 'true')` を打てば即解除可能。「実質無制限」は技術リテラシ低い層への防壁にすぎない。サーバーサイドのレート制限が `lib/rate-limit/server.ts` にあるが、PAID_MODE=false 時は「unused」とコメントされており、実際のスケール時に効いていない可能性。

3. **エラー追跡基盤の不在**: Sentry / Datadog 等のエラー追跡が見えない。フィードバックは「ユーザーが能動的に送ってくれた声」だけで、サイレント失敗（API 500、Gemini タイムアウト）が運営に届かない。MAU 1 万超で必ず破綻する。

4. **キャッシュ戦略の不在**: 12,162 問のデータを毎リクエストロードしている可能性。Vercel Edge / ISR を活用すべき。`generateStaticParams` の整備状況が見えない。

**致命的指摘 TOP3**:
1. メタデータが PAID_MODE ガード外（クリーン宣言と矛盾）
2. レート制限のサーバーサイド実装と localStorage 実装の二重構造の責任分界が曖昧
3. オブザーバビリティ（Sentry / メトリクス）が皆無

**改善 TOP3**:
1. 全 PAID_MODE ガード対象ページの metadata を `if (!PAID_MODE) return {}` 化
2. Sentry 導入 + AI 失敗率の自動計測
3. ISR + Vercel Edge Cache でデータロード最適化

**結論**: 設計思想は健全だが、運用への接地が不足。NPS = +10。

## 戦略妥当性判断

### 経営陣総括（西村・田島・黒田・小川）

- **不支持理由**: 成長 KPI を計測する仕組みが無く、「ピボットが成功か失敗か」を 6 ヶ月後に判定できない。出口戦略（売却 / 法人化 / 撤退）も見えない。

### 法務・税務総括（岡本・中島）

**現状は法的グレー。早急な整備が必要。**

- 個人運営前提なら開業届・利用規約・年次収支表が最低限必要。
- PAID_MODE 復活時の競業避止義務・職務専念義務リスクを所属企業と整理せよ。

### ユーザー総括（山田・中村・鈴木・渡辺）

**ユーザー体験は概ね高評価。ただし「教育貢献」ラベルへの疑念多い。**
