# 運用ランブック — 何が起きたら人が動くか

最終更新: 2026-08-01（Slack Webhook を本番へ登録し、実際に届くところまで確認した時点）

このファイルは「放置してよい状態か」を判断するための 1 枚。
監視する数値・通知が来る条件・来たときの対処・戻し方だけを置く。

---

## 1. まず知っておくこと

**AI 経路の失敗はほぼ HTTP 200 で返る。** 採点が字数ベースの簡易判定に落ちても、
JSON が出力上限で切れても、利用者には 200 とそれらしい画面が返る。
外形監視（ページが 200 か）は、この種の壊れ方を一切検知しない。
だから見るべきは HTTP ステータスではなく、下の 3 つの数値である。

## 2. 監視すべき数値

| 見るもの | どこで見るか | 正常 | 異常 |
| --- | --- | --- | --- |
| 月間 AI コスト | Upstash KV の `ai_cost:YYYY-MM`（JST 月次でキーが変わる） | 想定利用量なり | ¥40,000 で警告 / ¥50,000 で自動停止 |

## 3. 通知が来る条件

| 通知 | 発火条件 | 頻度の抑制 |
| --- | --- | --- |
| 月間コスト警告 | `ai_cost` が ¥40,000 を初めて超えたとき | その月 1 回だけ |
| 月間コスト上限 | `ai_cost` が ¥50,000 に到達したとき（同時に新規 AI を自動停止） | その月 1 回だけ |
| 採点フォールバック | 採点が簡易判定に落ちたとき（解析失敗 / 出力上限切れ） | 同一事象は 1 時間に 1 回 |
| 日次 404/410 検出 | 監視対象ルートが期待ステータスを返さないとき | 毎日 1 回 |
| 長期滞留 PR | 7 日以上オープンな PR があるとき（月曜 09:00 JST） | 週 1 回 |
| 利用者からの入力 | feedback / 問題コメント / 問題評価 / 問い合わせの投稿ごと | **抑制なし（1 投稿 = 1 通）** |

**通知しないもの（意図的）**

- `rate_limited`（429）… 無料枠・IP 制限は正常動作。件数が多く、鳴らすと他が埋もれる。
- `cost_capped`（503）… ¥50,000 到達時に 1 回通知済み。その後の 503 は帰結にすぎない。

### 通知先と、1 日に何通来るか

送信先は Slack ワークスペース `kameking-lab` の `#all-kameking-lab`
（レガシー Incoming Webhook。値は Vercel 本番 env `SLACK_WEBHOOK_URL` と
GitHub Secrets の同名 secret に登録済み）。

平常時の想定通数は **0〜1 通/日**。内訳:

- コスト警告・上限 … その月に閾値を越えたときだけ。月 **最大 2 通**
- 採点フォールバック … 壊れていなければ 0。壊れている間は key 4 種
  （`scoring:` / `essay-grade:` × `truncated` / `mock-fallback`）× 1 時間に 1 回で
  理論上限 96 通/日。**鳴り続けること自体が「継続中」のシグナル**
- 日次 404/410 … 不一致があるときだけ 1 通/日。現状は 45 ルート全一致で 0
- 長期滞留 PR … 週 1 通。滞留 PR が 0 件なら鳴らない
- 利用者からの入力 … 現状の実績で 1 通/3 日程度

**判定: 多すぎない。** ただし抑制が無いのは利用者入力だけなので、ここが
1 日 20 通を超えるようになったら、他の警報が埋もれる前に手を入れる
（`notifyOpsOnce` の cooldown 機構が既にあるので、それに寄せる）。

## 4. 通知が来たときの対処

### 月間コスト警告（¥40,000）

1. `ai_cost:YYYY-MM` の実数と、`rl:stats:*` のエンドポイント別件数を見る。
2. 想定利用の伸びなら放置してよい（上限で自動停止する）。
3. 想定外なら、`rl:topips:h:*`（時間別の IP 別件数）で偏りを見る。
   1 つの IP に偏っていれば濫用。偏りが無ければ純粋な利用増。

### 月間コスト上限（¥50,000）

新規 AI リクエストは自動停止済み（利用者には 503 と「翌月初に再開」の案内）。
**上限の引き上げは CLAUDE.md §0 で禁止されている。** 翌月 1 日に自動で復旧する。

### 採点フォールバック

通知本文の `finishReason` で分岐する。

- `MAX_TOKENS` … 出力上限で切れた。`app/api/scoring/route.ts` の `maxTokens`
  （記述 3000 / 論述 6000）と `gradingThinkingBudget` を見る。過去の事故は
  思考トークンが出力上限を食い潰したもので、`thinkingBudget: 0` で解決した。
- `STOP` なのに解析失敗 … モデルが JSON 以外を返している。`responseMimeType`
  が `application/json` のままか確認する。
- 単発なら放置してよい（1 時間に 1 回しか鳴らないので、鳴り続けるなら継続中）。

### 日次 404/410 検出

不一致ルートを本番で叩いて確認する。ルート側を直したのに監視の期待値が
古いだけ、というケースが実際にあった（`/pricing` が 410 に変わったのに
404 を期待し続け、毎日誤警報になっていた）。期待値の定義は
`lib/seo/expected-routes.ts` に一本化してある。

## 6. 通知経路の状態（2026-08-01 実測）

`SLACK_WEBHOOK_URL` は Vercel 本番 env と GitHub Secrets の両方に登録済み。
**設定しただけでなく、4 系統すべてを実際に `#all-kameking-lab` へ到達させて確認した。**

| 経路 | 確認方法 | 結果 |
| --- | --- | --- |
| コスト警告 / 上限 | `pnpm verify:cost-alert`（本番 KV は汚さない） | ¥39,999→0 通 / ¥40,001→1 通 / 超過継続→0 通 / ¥50,000→1 通 / 到達継続→0 通。設計どおり |
| 採点フォールバック | `buildGradingFallbackAlert` → `notifyOpsOnce` を実 Webhook 宛に通した | 到達（本文に `finishReason` / 思考トークンが載ることも確認） |
| 利用者からの入力 | 本番 `/api/contact` へ 1 件投稿 | 到達（**本番ランタイムから届いたので、env が実際に入っていることの証明**） |
| 長期滞留 PR | GitHub Actions を手動実行 | 到達（滞留 4 件を一覧で受信） |

日次ヘルスチェックは本番で実行して `ok: true` / 45 ルート中 0 不一致。
`/pricing` の 410 化で毎日誤警報になっていた問題は解消している。

## 7. AI を呼ぶ変更を入れるときの必須確認

CI が緑であることは、AI 応答の中身が正しいことを何も保証しない
（モックで走るテストは経路の形しか見ていない）。CLAUDE.md §7 のとおり、
Preview で 1 回実行して次の 3 点を目視するまで完了としない。

- `gradingMode` が `ai`（`simplified` は失敗）
- `finishReason` が `STOP`（`MAX_TOKENS` は切断）
- `ai_cost:YYYY-MM` が実測ぶん増える

## 8. 放置してよいかの判定（2026-08-01 時点）

| 条件 | 判定 | 根拠 |
| --- | --- | --- |
| 原価が想定外に跳ねる経路が塞がっている | 満たす | ¥50,000 で自動停止。KV 設定済みで計上が実際に効いている。上限の引き上げは CLAUDE.md §0 で禁止 |
| 異常が起きたら人が気づける | 満たす（端末側の通知設定を除く） | 通知 4 系統すべて実 Webhook への到達を確認済み（§6）。残るは受信端末の通知 ON |
| 次に作ったものが再び滞留しない導線がある | 満たす | 週次の滞留 PR 通知が Slack へ到達。Webhook が落ちても GitHub Issue にフォールバックする |

**結論: 放置してよい。** ただし「気づける」の最後の 1 歩は受信側にあり、
スマホの Slack 通知が切れていれば経路が生きていても気づけない。
